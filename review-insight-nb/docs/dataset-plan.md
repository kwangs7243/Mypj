# Dataset Plan

## Purpose

The current 20-row sample dataset is only for pipeline validation. The next phase needs larger and more varied datasets so model comparison is meaningful.

This project will use two dataset types:

1. Controlled synthetic datasets generated inside the project.
2. Real public Korean review datasets added later after checking source, license, and format.

## Korean Summary

현재 20개 샘플 데이터는 파이프라인 검증용이다. 다음 단계에서는 모델 비교가 의미 있으려면 더 크고 다양한 데이터셋이 필요하다.

이 프로젝트에서는 두 종류의 데이터셋을 사용한다.

1. 프로젝트 안에서 생성하는 통제된 synthetic 데이터셋
2. 출처, 라이선스, 형식을 확인한 뒤 추가할 실제 공개 한국어 리뷰 데이터셋

## Important Warning

Synthetic data generated by Codex or templates is useful for testing pipeline behavior, label balance, preprocessing, tokenization, and model comparison code.

It should not be treated as proof of real-world generalization performance.

Real performance claims require a real dataset with documented source and evaluation rules.

Large datasets should not be committed to Git. Store them externally, such as on a USB drive or another local data storage location, and keep only small samples, README files, scripts, and regeneration instructions in the repository.

## 중요한 주의점

Codex나 템플릿으로 생성한 synthetic 데이터는 파이프라인 동작, 라벨 균형, 전처리, 토큰화, 모델 비교 코드 검증에는 유용하다.

하지만 실제 서비스 일반화 성능을 증명하는 데이터로 해석하면 안 된다.

실제 성능을 주장하려면 출처와 평가 규칙이 명확한 실제 데이터셋이 필요하다.

큰 데이터셋은 Git에 커밋하지 않는다. USB나 별도 로컬 데이터 저장소에 보관하고, 저장소에는 작은 샘플, README, 생성 스크립트, 재생성 방법만 남긴다.

## Dataset Schema

Every dataset should keep this minimum schema:

```text
text,label
```

Allowed labels:

```text
positive
negative
```

Optional columns may exist in raw data, but training scripts should rely on `text` and `label`.

## Git Tracking Rule

- Track folder structure, README files, scripts, and small sample files.
- Ignore large raw/generated/processed/split dataset files.
- If a dataset must be used, document where to place it and which script generates or consumes it.
- If a vocabulary or dictionary is small and intentionally limited, it may be committed with a `_sample` or `_limited` suffix.
- Large tokenizer artifacts such as SentencePiece `.model` and `.vocab` files should stay ignored unless there is a clear reason to version a small limited artifact.

## Git 추적 규칙

- 폴더 구조, README, 스크립트, 작은 샘플 파일은 추적한다.
- 큰 raw/generated/processed/split 데이터셋 파일은 무시한다.
- 데이터셋을 사용해야 한다면 어디에 배치해야 하는지와 어떤 스크립트가 생성/사용하는지 문서화한다.
- 작고 의도적으로 제한된 단어사전은 `_sample` 또는 `_limited` suffix를 붙여 커밋할 수 있다.
- SentencePiece `.model`, `.vocab` 같은 큰 tokenizer artifact는 명확한 이유가 없는 한 Git에서 제외한다.

## Raw vs Processed

Raw/generated datasets may intentionally contain noisy text:

- Korean text
- inconsistent spacing
- numbers
- English words
- punctuation
- repeated expressions
- emojis or symbols

Processed datasets should be generated by explicit preprocessing rules.

Different preprocessing outputs may be saved separately later:

```text
processed/korean_only_5k.csv
processed/light_clean_5k.csv
processed/morph_tokenized_5k.csv
processed/sentencepiece_5k.csv
```

Current preprocessing modes:

```text
korean_only: keep only Korean characters and whitespace
light: normalize spacing only, preserving English, numbers, punctuation, and symbols
```

When generated review data is preprocessed, `korean_only` can produce fewer rows than `light` because removing English, numbers, and symbols can make more rows collapse into duplicate `text,label` pairs.

현재 전처리 모드:

```text
korean_only: 한글과 공백만 남긴다
light: 공백만 정리하고 영어, 숫자, 문장부호, 기호를 보존한다
```

생성 리뷰 데이터를 전처리할 때 `korean_only` 결과 행 수가 `light`보다 줄어들 수 있다. 영어, 숫자, 기호를 제거하면서 서로 다른 원문이 같은 `text,label` 조합으로 합쳐지고, 중복 제거 단계에서 삭제될 수 있기 때문이다.

## Why Keep Noisy Raw Text?

Noisy raw text is useful because later experiments can compare:

- simple Korean-only regex cleaning
- spacing normalization
- Korean morphological analysis
- SentencePiece subword tokenization
- whether English/numbers/symbols help or hurt

The current MVP removes English, numbers, punctuation, emojis, and symbols. Later experiments can decide whether that rule should change.

## 왜 지저분한 원본 텍스트를 남기는가?

지저분한 원본 텍스트를 남겨두면 이후 다음 항목을 비교할 수 있다.

- 단순 한글 전용 정규식 정제
- 공백 정리
- 한국어 형태소 분석
- SentencePiece subword 토큰화
- 영어, 숫자, 기호가 도움이 되는지 방해가 되는지

현재 MVP는 영어, 숫자, 문장부호, 이모지, 기호를 제거한다. 이후 실험에서 이 규칙을 바꿀지 판단한다.

## Dataset Creation Plan

### Step 1. Controlled Generated Dataset

Create a script that generates balanced Korean product review sentences from templates.

The generated dataset should include:

- product/service nouns
- positive and negative sentiment phrases
- delivery, price, quality, usability, customer service, packaging, refund, durability topics
- mild noise such as punctuation, repeated spaces, numbers, and occasional English words

Purpose:

- test preprocessing behavior
- test model comparison scripts
- test tokenizer experiments
- avoid relying on a tiny 20-row sample

### Step 2. Real Dataset Candidate

Later, choose a real Korean review dataset.

Selection criteria:

- Korean text
- binary or convertible sentiment labels
- clear source
- usable license
- manageable size for 16GB memory
- can be converted to `text,label`

### Step 3. Dataset Size Comparison

Use the same preprocessing/model settings and compare:

```text
5k vs 20k vs 50k
```

Goal:

- observe whether more data improves validation performance
- check training time
- check memory behavior
- find a practical dataset size for the project

## NSMC Dataset Plan

The generated 5k dataset is useful for validating the pipeline, but it is too easy for model comparison because template-based sentiment words make the test accuracy reach 100%.

Use NSMC as the next realistic Korean sentiment dataset.

Source:

```text
https://github.com/e9t/nsmc
```

NSMC provides Korean movie review sentiment data with this schema:

```text
id, document, label
```

Label meaning:

```text
0: negative
1: positive
```

Files to use:

```text
ratings_train.txt: 150,000 rows
ratings_test.txt: 50,000 rows
```

The files are tab-separated text files even though the extension is `.txt`.

Recommended project workflow:

```text
1. Place NSMC source files under backend/data/raw/.
2. Convert id/document/label to text,label.
3. Save converted files under backend/data/processed/ or backend/data/splits/.
4. Reuse compare_models.py with the converted train/test files.
```

Do not commit the NSMC raw or converted CSV files to Git. Keep only conversion scripts and instructions.

Korpora can also load Korean corpora through a Python package, but the first implementation should prefer raw files plus an explicit converter script. This keeps the data flow visible and avoids adding a dependency before it is needed.

## NSMC 데이터셋 계획

현재 generated 5k 데이터셋은 파이프라인 검증에는 유용하지만, 템플릿 기반 감성 단서가 너무 명확해서 모델 비교용으로는 너무 쉽다. test accuracy가 100%까지 나오므로 실제 일반화 성능 분석에는 부족하다.

다음 현실적인 한국어 감성분석 데이터셋으로 NSMC를 사용한다.

출처:

```text
https://github.com/e9t/nsmc
```

NSMC는 한국어 영화 리뷰 감성 데이터이며 기본 구조는 다음과 같다.

```text
id, document, label
```

라벨 의미:

```text
0: negative
1: positive
```

사용할 파일:

```text
ratings_train.txt: 150,000 rows
ratings_test.txt: 50,000 rows
```

파일 확장자는 `.txt`지만 내부 형식은 tab으로 구분된 TSV에 가깝다.

권장 프로젝트 흐름:

```text
1. NSMC 원본 파일을 backend/data/raw/ 아래에 둔다.
2. id/document/label 구조를 text,label 구조로 변환한다.
3. 변환 결과를 backend/data/processed/ 또는 backend/data/splits/ 아래에 저장한다.
4. 변환된 train/test 파일을 compare_models.py에 넣어 재사용한다.
```

NSMC 원본 파일이나 변환 CSV는 Git에 커밋하지 않는다. 변환 스크립트와 실행 안내만 저장소에 남긴다.

Korpora 라이브러리로 한국어 말뭉치를 가져오는 방식도 가능하지만, 첫 구현에서는 원본 파일과 명시적인 변환 스크립트를 우선 사용한다. 데이터 흐름을 눈으로 추적하기 쉽고, 필요한 시점 전까지 의존성을 늘리지 않을 수 있기 때문이다.

## Next Dataset Task

Create a controlled generated dataset script:

```text
backend/ml/experiments/generate_review_dataset.py
```

Expected first output:

```text
backend/data/generated/generated_reviews_5k.csv
```

Run command:

```bash
cd review-insight-nb/backend
uv run python ml/experiments/generate_review_dataset.py
```

Then run preprocessing to create:

```text
backend/data/processed/korean_only_5k.csv
```

Command:

```bash
cd review-insight-nb/backend
uv run python ml/preprocess.py --input data/generated/generated_reviews_5k.csv --output data/processed/korean_only_5k.csv --mode korean_only
uv run python ml/preprocess.py --input data/generated/generated_reviews_5k.csv --output data/processed/light_clean_5k.csv --mode light
```

Then create fixed train/test splits:

```bash
uv run python ml/experiments/split_dataset.py --input data/processed/korean_only_5k.csv --train-output data/splits/korean_only_5k_train.csv --test-output data/splits/korean_only_5k_test.csv
uv run python ml/experiments/split_dataset.py --input data/processed/light_clean_5k.csv --train-output data/splits/light_clean_5k_train.csv --test-output data/splits/light_clean_5k_test.csv
```

The split files are also ignored by Git.

그 다음 고정된 train/test 분할 파일을 만든다.

```bash
uv run python ml/experiments/split_dataset.py --input data/processed/korean_only_5k.csv --train-output data/splits/korean_only_5k_train.csv --test-output data/splits/korean_only_5k_test.csv
uv run python ml/experiments/split_dataset.py --input data/processed/light_clean_5k.csv --train-output data/splits/light_clean_5k_train.csv --test-output data/splits/light_clean_5k_test.csv
```

split CSV 파일도 Git에서 무시된다.

These output CSV files are ignored by Git. After cloning on another PC, run the generation/preprocessing scripts again or copy the dataset from external storage.

위 출력 CSV 파일들은 Git에서 무시된다. 다른 PC에서 clone한 뒤에는 생성/전처리 스크립트를 다시 실행하거나 외부 저장소에서 데이터셋을 복사한다.
